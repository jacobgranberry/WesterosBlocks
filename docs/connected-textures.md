# Connected textures (WesterosContinuity) in WesterosBlocks

Reference for agents and contributors who touch anything under
`assets/*/optifine/ctm/`, block textures that those files match, the
`connectstate` block property, or the `*_ctm` / `connect_*` block tags.
Connected textures (CTM) are a large part of how this mod looks, so read this
before changing any of them.

Everything here targets Minecraft 1.21.1. Facts about WesterosContinuity come
from its source, not only its docs, because the two disagree in places (noted
below).

## Quick facts

- The client mod is **WesterosContinuity**, a fork of **Continuity** (Fabric).
  It reads OptiFine-format CTM `.properties` files. It is not a Gradle
  dependency, so `runClient` shows plain textures. That is expected.
- The mod ships 1,403 `.properties` files (1,339 in the `westerosblocks`
  namespace, 64 in `minecraft`) and about 16,900 tile PNGs, almost all 32x32.
- The fork adds two properties: `connect_to_tag=<block tag>` and
  `connect_to_states=<property>[,<property>...]`. The key is
  **`connect_to_states` (plural)** in the code. The Modrinth page and the old
  conversion script say `connect_to_state`, which the mod ignores.
- `connect_to_states=connectstate` relies on the `connectstate` block property
  (`ModProperties.CONNECTSTATE`, an int 0 to 3). Changing whether a block has
  that property changes its blockstates, which breaks placed blocks. See the
  compatibility rule in [AGENTS.md](../AGENTS.md).
- `connect_to_tag` tags are generated by datagen (`ModBlockTagProvider`). They
  only exist in a build after `./gradlew runDatagen`.
- Continuity ignores `layer` on non-overlay methods, `connect` on non-connecting
  methods, and `weight` everywhere. The block's own render layer decides
  transparency (see [Render layers](#render-layers)).
- Files are applied in alphabetical order of their path; the first file whose
  conditions match a quad wins. Biome variants depend on this.

- `model/CtmBakedModel.java`: the per-quad pipeline and multipass (4 passes).

## How WesterosContinuity applies a file

1. **Loading.** It scans `assets/<any namespace>/optifine/ctm/**.properties` in
   every resource pack (OptiFine only scans `minecraft`). A missing `method`
   means `ctm`. An unknown method is logged and skipped.
2. **Matching.** A file applies to a quad when the quad's sprite is in
   `matchTiles`, or the block state matches `matchBlocks`. A file named
   `block_<id>.properties` with no `matchBlocks` matches that block. Every
   file in this repo uses `matchTiles`.
3. **Order.** Files with `prioritize=true` come first. The default is true when
   `matchTiles` is set, so in practice every file here is prioritized. Next,
   higher resource-pack priority comes first. Last, the resource id is compared
   (path first, then namespace), alphabetically. For each quad the first file
   whose conditions (`faces`, `biomes`, `heights`, `name`) pass replaces the
   sprite. Failing conditions fall through to the next file. If none apply, the
   original sprite stays.
4. **Multipass.** After a file replaces a sprite, the new sprite can be matched
   again by a file whose `matchTiles` names a CTM output tile (a path under
   `optifine/`). Up to 4 passes run. The bark files use this, for example
   `bark/birch/repeat_left.properties` with `matchTiles=./side/0`.
5. **Tile choice.** The method picks one of `tiles` from the neighbors (see
   [Methods](#methods-and-tile-layouts)).

### Path rules

`matchTiles` (and `connectTiles`), space separated:

| Written as | Resolves to sprite |
|---|---|
| `westerosblocks:textures/block/foo/bar` (what this repo uses) | `westerosblocks:block/foo/bar` |
| `minecraft:textures/block/glass` | `minecraft:block/glass` |
| `dirt` (no namespace, no `/`) | `minecraft:block/dirt` |
| `./side/0` | the CTM tile `optifine/ctm/<this file's folder>/side/0.png` in this file's namespace (multipass) |
| `optifine/ctm/a/b/26` | that CTM tile in this file's namespace (multipass) |

A `.png` suffix is stripped. A bare name such as `26` is **not** relative to
the file; it means `minecraft:block/26`.

`tiles`, separated by spaces or commas:

| Written as | Resolves to |
|---|---|
| `side/0` (what this repo uses) | `<this file's folder>/side/0.png`, in this file's namespace |
| `0-46` | `0.png` to `46.png` in this file's folder |
| `<skip>` / `<default>` | skip this tile (overlays) / keep the original sprite |
| `ns:path` | namespaced: no `/` means `textures/block/`, otherwise relative to `textures/` unless it starts with `textures/` or `optifine/`; ranges are not expanded |

## Properties

General (all methods):

| Property | Continuity behavior |
|---|---|
| `method` | Required in practice; default `ctm`. |
| `matchTiles`, `matchBlocks` | At least one is required (or a `block_` file name). `matchBlocks` syntax: `ns:block:prop=v1,v2:prop2=v`. |
| `tiles` | Required. Count rules per method below. |
| `faces` | `bottom top north south east west sides all`. |
| `biomes` | Space separated ids. A leading `!` negates the whole list. Unknown ids log `Unknown biome` and never match. |
| `heights` | `min-max`, with negatives in brackets `(-64)-35`, or Continuity's `-64..35`, `..35`, `-64..`. `minHeight`/`maxHeight` also work. |
| `name` | Nameable block entities only. |
| `weight` | **Ignored** by Continuity. Order comes from file names (see above). |
| `prioritize` | Continuity only. Default true if `matchTiles` is set. |
| `orient` | Continuity only: `NONE`, `STATE_AXIS`, `TEXTURE`. Default `TEXTURE` for ctm, ctm_compact, horizontal, vertical, h+v, v+h; `NONE` otherwise. |
| `resourceCondition`, `optifineOnly` | Continuity only; unused here. |

Connecting methods (`ctm`, `ctm_compact`, `horizontal`, `vertical`,
`horizontal+vertical`, `vertical+horizontal`, `top`, `overlay`, `overlay_ctm`,
`overlay_horizontal`, `overlay_vertical`, `overlay_h+v`, `overlay_v+h`):

| Property | Behavior |
|---|---|
| `connect` | `block` (same block), `tile` (neighbor shows the same sprite on that face), `state` (identical block state). Default `block` if `matchBlocks` is set, else `tile`. Ignored when `connect_to_tag` or `connect_to_states` is present. |
| `connect_to_tag` | WesterosContinuity only. See [Connection rules](#connection-rules). |
| `connect_to_states` | WesterosContinuity only. See [Connection rules](#connection-rules). |
| `innerSeams` | Continuity also honors it for horizontal, vertical, h+v, v+h and top. |

`random`, `repeat` and `fixed` do not connect, so `connect`, `connect_to_tag`
and `connect_to_states` do nothing there.

Method specific: `width`/`height` (repeat; tiles must equal width x height),
`weights`/`randomLoops`/`linked` (random), `symmetry` (random:
`none|opposite|all`; repeat: `none|opposite`), `ctm.<n>=<tile>` (ctm_compact),
`connectTiles`/`connectBlocks`/`tintIndex`/`tintBlock`/`layer` (overlay
methods only).

## Methods and tile layouts

Counts are what `ContinuityClient` enforces. "At least" means extra tiles are
allowed.

| Method | Tiles | Used here | Notes |
|---|---|---|---|
| `ctm` (alias `glass`) | at least 47 | 212 | 8-way. Tile 0 is the unconnected tile; tile 26 is the fully surrounded interior tile. Layout follows OptiFine's 47-tile template. |
| `ctm_compact` | at least 5 | 1 (demo) | 4 quarter tiles plus `ctm.<n>` overrides. Not compatible with overlays. |
| `horizontal` (alias `bookshelf`) | exactly 4 | 100 | 0 = left end (neighbor on the right only), 1 = middle, 2 = right end, 3 = alone. |
| `vertical` | exactly 4 | 472 | 0 = bottom end (neighbor above only), 1 = middle, 2 = top end, 3 = alone. |
| `horizontal+vertical` (`h+v`) | exactly 7 | 2 | Horizontal first; in Continuity a face already joined horizontally does not also join vertically. |
| `vertical+horizontal` (`v+h`) | exactly 7 | 1 | The reverse. |
| `top` | exactly 1 | 0 | Side faces connect to the block above. |
| `random` | any | 40 | `weights`, `symmetry`, `linked`, `randomLoops`. |
| `repeat` | width x height | 419 | Fixed pattern by world position. |
| `fixed` | exactly 1 | 156 | Used here to swap a texture by biome or to apply a tile unconditionally. |
| `overlay*` | 17 / 47 / any / w x h / 1 / 4 / 7 | 0 | Overlays render on top of the base quad and honor `layer`. None used yet. |

"Left", "right", "above" and "below" are in texture space (`orient=TEXTURE`).

## Connection rules

Upstream `connect` compares the current block with each neighbor. The fork's
two properties replace that comparison (`BasicConnectingCtmProperties`):

| Present in file | Two blocks connect when |
|---|---|
| `connect_to_tag=T` only | **both** blocks are in block tag `T`. Different blocks can connect. A block that shows the texture but is not in the tag never connects, so it always gets the unconnected tile. |
| `connect_to_states=P` only | same block **and** both have property `P` with equal values. |
| both | both in tag `T` **and** equal values of `P`. |
| neither | normal `connect` (or its default). |

Details from the code:

- `connect_to_states` takes a comma-separated list; every listed property must
  exist on both blocks and be equal. A block without the property never
  connects.
- The checks use the neighbor's appearance state, and the tag is a normal block
  tag (`TagKey<Block>`), so it must exist in the loaded data: the tags the mod
  jar ships (on a server, the server's copy).
- `connect_to_tag` is ignored on `random`, `repeat` and `fixed` (they never
  connect).

## How WesterosBlocks uses it

### File layout and naming

- `assets/westerosblocks/optifine/ctm/<path>.properties` matches the texture
  `westerosblocks:block/<path>` and keeps its tiles in the folder
  `<path>/` next to it (`<path>/0.png`, `<path>/1.png`, ...). Tiles are
  referenced as `<name>/<n>`, relative to the file.
- `assets/minecraft/optifine/ctm/` changes **vanilla** blocks too: wool,
  oak/birch/spruce/jungle planks, glass, iron block, snow, dirt, farmland,
  sandstone, red sandstone, bookshelf and vine. Some match textures the mod adds
  for those vanilla blocks under `westerosblocks:block/vanilla/` (for example
  `matchTiles=westerosblocks:textures/block/vanilla/dirt/top_bot1`).
- Biome or height variants of one texture are separate files: `<name>_a`,
  `<name>_b`, ... with `biomes=`/`heights=`, and `<name>_default` with the
  negated union of all the others' biomes (`biomes=!...`). Because the default
  excludes the others, the order does not matter even though `_default` sorts
  before `_e`. Keep that property when you edit one of them.
- Multipass chains use `matchTiles=./<tile folder>/<n>` (bark, mossy bark).
- Folder `ctm/ctm/` holds the test and demo blocks for each method.

Method use, by count: vertical 472, repeat 419, ctm 212, fixed 156, horizontal
100, random 40, h+v 2, v+h 1, ctm_compact 1. Connect use: `connect=block` 401,
`connect=state` 342, `connect_to_tag` 97, `connect_to_states` 70, none 660
(mostly non-connecting methods).

### Where the files came from

On 1.18.2 the mod used the Forge ConnectedTexturesMod format: CTM definitions in
each texture's `.png.mcmeta`, with custom `westeros_*` types (for example
`westeros_ctm`, `westeros_pattern`, `westeros_ctm+pattern`, `westeros_cond`) and
`extra.connect_to_tag` / `extra.connect_to_state`. The
`scripts/ctm_to_continuity.py` script converted those to OptiFine `.properties`
and 32x32 tiles. Its method map:

| 1.18.2 type | Now |
|---|---|
| `normal` | `fixed` |
| `ctm` | `ctm_compact` |
| `pattern`, `westeros_pattern` | `repeat` |
| `ctm_vertical`, `westeros_vertical`, `westeros_pillar` | `vertical` |
| `ctm_horizontal`, `westeros_horizontal` | `horizontal` |
| `westeros_h+v`, `westeros_v+h` | `horizontal+vertical`, `vertical+horizontal` |
| `westeros_ctm`, `westeros_ctm_single` | `ctm` |
| `westeros_ctm+pattern` | `ctm` plus a nested `repeat` file `<name>/26.properties` for the interior tile |
| `*_cond` (biome or height conditions) | one file per condition plus `_default` |

The script is stale. It writes `connect=state:<p>` and `connect=tag:<t>`, which
the files no longer contain, so the committed files were edited after it ran.
Its docstring also predates the fork. Treat the committed `.properties` files
as the source of truth. There is no datagen for CTM; the files are written by
hand (or by one-off scripts).

### The `connectstate` property

- `ModProperties.CONNECTSTATE` is `IntProperty.of("connectstate", 0, 3)`.
- Blocks opt in with `"options": {"connectstate": true}` in
  `definitions/WesterosBlocks.json` (226 standalone `solid` blocks), or per
  variant in a block set (`"options": {"solid,slab": {...}, "stairs,wall": {...}}`,
  26 sets). `WCSolidBlock`, `WCSlabBlock`, `WCStairBlock` and `WCWallBlock`
  add the property.
- New placements get `connectstate=0`. Nothing in the mod changes it after
  that: the creative right-click toggle cycles the block's `state` property,
  not `connectstate`. It has to be set with an outside tool such as the debug
  stick or WorldEdit.
- 70 files use `connect_to_states=connectstate` (ctm 50, horizontal 12,
  vertical 8). Builders use it to split one wall of the same texture into
  separately connected groups.
- Adding or removing `connectstate` on an existing block changes its
  blockstates. Do not do that without a migration.

### Tags used by `connect_to_tag`

| Tag | Files | Members come from |
|---|---|---|
| `westerosblocks:polished_stone_ctm` | 26 (`ashlar_full/*/all`, all also `connect_to_states=connectstate`) | block sets' `customTags` (every variant of the 26 `*_polished` sets) |
| `westerosblocks:wool_ctm` | 16 (`wool/*/all`) | block sets' `customTags` (the 16 wool sets) |
| `westerosblocks:wool_block_ctm` | 16 (`wool/*/block`) | `altCustomTags.solid` of the wool sets, plus vanilla wool in `block_tags.json` |
| `westerosblocks:wood_ctm` | 18 | `altCustomTags.solid` of the 14 wood sets, plus vanilla planks in `block_tags.json` |
| `westerosblocks:plank_ctm` | 17 | `altCustomTags["stairs,slab,wall,hopper,tip"]` of the wood sets, plus vanilla wooden stairs and slabs |
| `westerosblocks:connect_grassy_sand` | 3 (`grassy_sand/side_*`) | `block_tags.json` (sand, grassy sand, its slab and layer) |
| `westerosblocks:connect_muddy_sand` | 1 (`muddy_sand/side`) | `block_tags.json` (wet sand, muddy sand, slabs, layers) |

`definitions/block_tags.json` lists explicit members.
`ModBlockTagProvider` adds every block whose definition or block set declares
the tag. Both write to `src/main/generated/data/westerosblocks/tags/block/`,
which is gitignored.

### Render layers

The block's render layer is set in `WesterosBlocksClient`: the definition's
`renderLayer`, else `cutout` when it has `overlayTextures`, else `translucent`
when `alphaRender` is set. Block sets give `cutout` to arrow slits and window
frames (`BlockSetExpander`). A CTM tile with transparent pixels needs a
non-solid block layer. The `layer=` line in 678 non-overlay files is left over
from 1.18.2, where CTM could force a layer per texture. Continuity ignores it.
If a tile must render cutout on a solid block, either give the block a
`renderLayer` or switch the file to an `overlay_*` method.

## Known problems (checked 2026-11-07)

Found with a static check of all 1,403 files against the parsing rules above
and against `definitions/WesterosBlocks.json`. None of them crash; they make
some files do nothing. Confirm in game before fixing, and remember that some
fixes change how existing builds look.

1. **Interior repeat patterns never apply (5 files).** These nested files from
   the `westeros_ctm+pattern` conversion use `matchTiles=26`, which resolves
   to `minecraft:block/26`, a texture that does not exist:
   `ctm/westerosctmpattern/26.properties`,
   `grassy_sand/side_a/26.properties`, `grassy_sand/side_b/26.properties`,
   `grassy_sand/side_default/26.properties`, `muddy_sand/side/26.properties`.
   Their intent is to tile the interior CTM tile (26) with a repeat pattern.
   The likely fix is `matchTiles=./26`, the same form the bark files use.
   Untested; it changes how existing grassy and muddy sand surfaces look.
2. **The connected wood and plank textures are not wired up (36 files).**
   `wood/*/woodctm.properties`, `wood/*/plankctm.properties` (14 colors each)
   and `minecraft/optifine/ctm/{oak,birch,spruce,jungle}_planks-woodctm.properties`
   match `wood/<color>/woodctm`, `wood/<color>/plankctm` and
   `minecraft:block/<wood>_planks-woodctm`. No block or model uses those
   textures, and the base PNGs are not in the repo. On 1.18.2 the wood sets used
   them through `altTextures` (for example
   `"solid": ["wood/oak/all", "wood/oak/all", "wood/oak/woodctm"]`) and a
   `westeros_ctm` `.mcmeta`. The port's wood sets use `cut`/`base` states with
   `all_lines`/`all` instead. So the `wood_ctm` and `plank_ctm` tags currently
   connect nothing. Decide whether connected wood should come back before
   deleting or rewiring these.
3. **Orphaned roofing files (6 files).** `roofing/tiles/tiles_0` to `tiles_5`
   match `westerosblocks:block/roofing/tiles/tiles_N`, which does not exist.
   They look left over from before the roofing rename (commit `ad98a803`);
   the current roofing textures are `beavertail`, `imbrex` and `shingle`. The demo
   `ctm/pillar.properties` is also unused.
4. **`connect_to_tag` on non-connecting methods (3 files).**
   `minecraft/optifine/ctm/{oak,spruce,jungle}_planks.properties` are `repeat`
   files, so their `connect_to_tag=westerosblocks:plank_ctm` does nothing. They
   still repeat-texture vanilla planks.
5. **Pre-1.18 biome ids (2 files).** `grassy_sand/side_b.properties` and
   `grassy_sand/side_default.properties` list `minecraft:taiga_mountains`,
   `minecraft:extreme_hills` and `minecraft:taiga_hills`. They don't exist in
   1.21.1, so they log a warning and match nothing. The modern ids are already
   in the same lists, so behavior is right; remove them to quiet the log.
6. **Wrong mod id in `fabric.mod.json`.** It `suggests` `westeroscontinuity`,
   but the fork's id is `westeros-continuity`, so the hint never matches.
   Harmless.
7. **No-op lines.** `layer=` on 678 non-overlay files and `connect=` on 93
   `fixed` files are ignored. `awning_red` uses `wool/red/all` but is not in
   `wool_ctm`, so its faces always show the unconnected tile (probably fine).

Things that were checked and are fine: every referenced tile PNG exists; every
method has a valid tile count (all `ctm` files have exactly 47, every `repeat`
has width x height tiles); every `connect_to_states` texture is used only by
blocks that have `connectstate`; every block using a `polished_stone_ctm` or
wool texture is in the matching tag; all biome variant groups are mutually
exclusive; the three `heights` ranges parse.

## Checklist for adding or changing connected textures

1. Find which texture the block's model really uses (datagen output in
   `src/main/generated/assets/westerosblocks/models/`, or the definition's
   `textures`). `matchTiles` must name exactly that sprite:
   `westerosblocks:textures/block/<path>`.
2. Put the file at `optifine/ctm/<path>.properties` and its tiles in
   `optifine/ctm/<path>/`, as 32x32 PNGs referenced `<name>/<n>`.
3. Pick a method and give it exactly the tile count in the table above.
4. Pick the connection rule. Prefer `connect=block` or `connect=state`. Use
   `connect_to_tag` when different blocks (for example solid and slab) must
   join, and add those blocks to the tag through `customTags`/`altCustomTags` or
   `block_tags.json`. Use `connect_to_states=connectstate` only on blocks that
   already have `connectstate`.
5. Never add or remove `connectstate` on an existing block, and never rename a
   texture an existing CTM file matches, without accounting for placed blocks
   and existing builds.
6. If tiles have transparency, make sure the block's render layer is not solid.
7. For biome variants, write `_a`, `_b`, ... and a `_default` whose negated list
   is the union of the others.
8. Test with WesterosContinuity installed (the dev client does not load it).
   F3+T reloads resources. Look for `Continuity` warnings in `latest.log`:
   unknown biome, invalid tiles, "No tile or block matches", tile count errors.
