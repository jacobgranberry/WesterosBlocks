# AGENTS.md

Guidance for AI coding agents working in this repository. Humans are welcome to
read it too. `CLAUDE.md` imports this file and adds only Claude Code specifics,
so put shared guidance here.

## What this is

WesterosBlocks is a Minecraft mod (mod id `westerosblocks`) that adds thousands
of decorative blocks for the WesterosCraft server. Blocks are data-driven: they
are declared in JSON and turned into blocks, block states, models, tags and lang
entries at startup and in datagen.

This branch (`1.21.1-fabric`) is a port of the upstream **Forge 1.18.2** mod to
**Fabric on Minecraft 1.21.1**.

- Stay on Minecraft 1.21.1. Do not bump `minecraft_version`, Yarn, Fabric API or
  Loom to a newer Minecraft line.
- Java 21, Yarn mappings (not Mojang mappings). Use Yarn names such as
  `BlockState`, `Identifier`, `VoxelShape`, `appendProperties`.
- Versions live in `gradle.properties`.

## Hard rule: existing worlds must load unchanged

The server has large builds made of these blocks. **Never change the registry
name, block state properties (names, values, defaults) or blockstates of an
existing block without a migration or compatibility path.** A change that
renames or drops a block or state value silently corrupts placed blocks.

Things that count as a change to an existing block:

- Renaming or removing a `blockName`, or changing a block set's name or its
  variant list (block sets expand into one block per variant, so this renames or
  removes many blocks at once; see `data/BlockSetExpander.java`).
- Changing `blockType`, `states` / `stateID`s, or options that add or remove
  properties (for example waterlogging, toggles, connection sides).
- Java changes to `appendProperties`, property declarations or default states in
  `block/custom/WC*Block.java` or `utils/ModProperties.java`.

Adding new blocks is fine. If a change could touch existing state lists, prove it
does not: dump every registered block's state list before and after and diff
them. Say in the PR how you checked.

`data/BlockCompatibilityValidator.java` is meant to enforce this at startup, but
its baseline `src/main/resources/definitions/known_blocks.json` has not been
committed yet, so the subsume check is currently skipped. Do not rely on it.
See `data/KnownBlocksExporter.java` for how a baseline is produced.

## Do not port

These upstream features were removed on purpose. Do not port them back or flag
them as missing:

- The `sound` block type (and its ~90 sound files).
- The `/ptime`, `/pweather` and `/nv` commands, their packets and mixins. They
  live in another mod now.

## Client mods the assets rely on

The modpack runs two client-side mods that this mod's resources are written
for. Both are only `suggests` in `fabric.mod.json` and are not Gradle
dependencies, so the dev client from `runClient` does not load them. Use the
versions for Minecraft 1.21.1 and read their docs before editing these files.

**Polytone** ([wiki](https://github.com/MehVahdJukaar/polytone/wiki)) is a
resource-pack extension mod.

- Files: `assets/*/polytone/` (`colormaps/`, `block_modifiers/`,
  `custom_particles/`, `fluid_modifiers/`). Block colormap modifiers are
  generated by `datagen/providers/ModPolytoneProvider.java` from each block's
  `colorMult`/`colorMults`; particle emitters (`WCParticleEmitterBlock`) use the
  custom particles.
- Polytone lets block models use rotation angles vanilla rejects (vanilla only
  allows -45, -22.5, 0, 22.5 and 45). Models here use angles such as 135, 180,
  26.5 and -20 on purpose. Do not "fix" them to vanilla angles. Model errors
  about these angles in the dev client log appear only because Polytone is not
  loaded there; they are not bugs.

**WesterosContinuity** ([Modrinth](https://modrinth.com/mod/westeroscontinuity))
is a fork of Continuity that adds connected textures. Follow the
[Continuity Connected Textures Specification](https://github.com/PepperCode1/Continuity/wiki/Continuity-Connected-Textures-Specification),
which uses the OptiFine CTM `.properties` format.

- Files: `assets/*/optifine/ctm/**.properties` plus their tile PNGs (about
  1,500 files; methods `ctm`, `ctm_compact`, `fixed`, `horizontal`, `vertical`,
  `repeat`, `random`).
- `scripts/ctm_to_continuity.py` converts the old upstream CTM format to this
  one.
- Without the mod, blocks show their base texture; that is expected in the dev
  client.

## Build and run

```bash
./gradlew runDatagen   # generate blockstates, models, tags, lang into src/main/generated/
./gradlew runClient    # launch a dev client
./gradlew build        # jar in build/libs/
```

- Gradle must reach `maven.fabricmc.net` (Loom, Yarn, Fabric API). Sandboxes
  that block that host cannot build at all; say so instead of guessing whether
  code compiles.
- `src/main/generated/` is gitignored and `build` does not depend on
  `runDatagen`. Run `runDatagen` first after changing definitions or exporters,
  or the client and jar will use stale or missing assets.
- There are no unit tests (`src/test` does not exist) and **no CI, by choice**.
  Do not add a CI workflow. Verify with `runDatagen` and `build`, and with
  `runClient` for visual or behavioral changes.

## Layout

```
src/main/resources/definitions/
  WesterosBlocks.json   # every block: {"blocks": [...], "blockSets": [...]} (~2 MB)
  block_tags.json       # extra tag membership
  color_maps.json       # biome/color tint maps
schemas/                # JSON Schemas for the definitions file (keep in sync)
src/main/java/com/westerosblocks/
  WesterosBlocks.java             # main entrypoint: load defs, validate, register
  WesterosBlocksClient.java       # client entrypoint: renderers and client setup
  WesterosBlocksDataGenerator.java# datagen entrypoint
  block/BlockTypes.java           # the one list of block types ("solid", "stair", ...)
  block/custom/WC*Block.java      # one class per type, each with a nested Factory
  block/ModBlocks.java            # registration from definitions
  data/                           # definition model, loaders, block-set expansion, validator
  datagen/providers/              # Fabric datagen providers (models, lang, tags, Polytone)
  datagen/custom/*Exporter.java   # per-type blockstate/model generation
src/main/resources/assets/westerosblocks/  # textures, hand-made models, sounds, geo
scripts/                # one-off Python tools (CTM to Continuity conversion)
```

`definitions/WesterosBlocks.json` is the source of truth for blocks. Array order
is authoritative and drives creative-tab order. It is large: search it with
`grep` or a JSON tool rather than reading it whole.

## Common tasks

**Add or change a block.** Edit `definitions/WesterosBlocks.json`, keeping it
valid against `schemas/westerosblocks.schema.json`. Textures go under
`assets/westerosblocks/textures/block/`. Then `runDatagen` and check the result
in `runClient`. Mind the hard rule above for existing blocks.

**Add a block type.** Add one entry in `block/BlockTypes.java` (id, factory,
tags, traits), a `WC*Block` class with a `Factory` in `block/custom/`, an
exporter in `datagen/custom/` registered in `ModModelProvider`'s `EXPORTERS`
map (datagen fails if it is missing), and the type in
`schemas/block-definition.schema.json`.

**Port something from upstream.** Read the matching upstream 1.18.2 Forge code,
then reimplement it with Fabric API and Yarn names. Keep upstream behavior,
block names and state values identical so 1.18.2 worlds still load.

## Git and pull requests

- Work on a feature branch off `1.21.1-fabric` and open PRs against
  `1.21.1-fabric` on **`jacobgranberry/WesterosBlocks`** (Jacob's fork).
- **Never push to or open PRs on `WesterosCraft/WesterosBlocks`.** On Jacob's
  machine that upstream repo is the `origin` remote and the fork is `fork`, so
  push with `git push fork <branch>` there. Check `git remote -v` before pushing
  anywhere.
- Keep PRs focused; several refactors may be open at once, so avoid unrelated
  edits to shared files.
